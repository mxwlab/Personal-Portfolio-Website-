## 一、目标与决策（已确认）

已拍板的决策：

| 项 | 决定 |
|---|---|
| 改造幅度 | **全面重构**（按故事线主张重写，不是润色） |
| 页面深度 | **精炼、可扫描的落地页**（非长文案例；每屏一个立论） |
| 视觉素材 | **暂不用真实截图**，沿用 CSS 画的抽象图形/示意 |

## 二、统一文案规则：两层写法

每条设计决策都拆成两层，**永远不让专业术语当第一句**：

- **上层（人人秒懂）**：一句大白话，讲清这个决策的"聪明"在哪，不含术语。HR 也能读。
- **下层（证据）**：一行具体例子，可含术语，但术语一律翻译成人话（`LCL`→"控制下限"、`子组34`→"第 34 组数据"、`RID`→"唯一编号"），只保留**一次**原始术语/编号当可信度锚点。

目的：非专业招聘方读上层就懂并被"具体感"打动；懂行的用人经理读下层被说服。删术语会丢说服力，所以不删，只是不让它打头。

## 三、页面结构与文案草稿

顺序即叙事：先抛后果制造信任缺口，再逐层展示"我为让这句结论可被验证做了什么"，最后收成可迁移原则。

### 1. Hero — 主句开场
- Eyebrow：`Primary Case · Industrial AI · Semantic Base`
- H1：**工业智能语义基座**
- 主句（锁定）：
  > 在工业质量场景里，AI 的一句结论可能让一条产线停机。
  > 我做的，是决定每一层里什么交给 AI、什么留给人——让一线工程师始终能自己核对、甚至推翻机器。
- 一句背景+角色：这是一个**通用的工业智能语义基座**（本体 + Agent 平台），当前以**铁路轴承制造质量**为首个落地场景，能力成熟后将扩展到更多工业场景；我负责从数据接入、本体建模，到质量 Agent 与沙盘推演的交互设计。
  - 注意：平台是通用的，轴承只是首个试点，不能写成"面向轴承的平台"。此点与 §5 结尾句"轴承只是它们第一次被验证的地方"首尾呼应。
- 右侧视觉：把现有 knowledge-map 改成**三层结构图**（纯 CSS），标签一律说人话，不用行话：
  - **应用层** —— Agent 和人用它做质量分析、沙盘推演（原"消费层"，避免"消费"歧义）
  - **本体层** —— 定义有哪些对象、怎么连、谁能改（"本体"是产品核心词，保留，可加一句注解）
  - **数据层** —— 把工厂数据接进来（原"底层/数据连接"）

### 2. 平台全景 — 先让人看见这是个重量级平台（确立广度）

> 结构职能：**广度/地图**。承接 Hero，让读者先建立"这是覆盖全链路的大平台"的认知，再进入张力与深挖。放在立论之前，是为了让「立论（问题）→ 签名决策（答案）」紧挨、中间不被架构图打断。

一屏架构总览，把三层九个模块全部摊开，每个模块**只一句话带过**（全面但不深）。

- 定调句：**这是一个覆盖「数据接入 → 本体建模 → Agent 应用」全链路的工业智能语义基座。下面每一层，我都做了人与 AI 的边界取舍。**
- 三层九模块（纯 CSS 架构图/表）：

  | 层 | 模块（各一句话） |
  |---|---|
  | **应用层** | 实体库 · 质量 Agent · 沙盘推演 |
  | **本体层** | 对象类型 · 链接类型 · 操作类型 · AI 图标库 |
  | **数据层** | 数据连接 · AI 管道生成器 |

- 九个模块在此**全部露脸**；其中 **5 个模块**（质量 Agent、沙盘、链接类型、实体库、AI 管道生成器）在 §4 深讲，其余（数据连接、对象类型、操作类型…）在这一句话里露出即可，不遗漏、不抢戏。

### 3. 立论 — H2：AI 说"立即停机"——凭什么有人敢按？

> 结构职能：**张力/问题**。镜头从"平台全貌"推近到最危险的那一点（质量 Agent 的停机结论），抛出一个问题——然后**直接交棒给签名决策**。它是问题，§4 是答案，两者必须紧挨。相对 Hero 是**升级不是复读**：Hero 抽象说"可能让产线停机"，这里把**真实的"立即停机"结论卡**摆出来，加上担责张力。

- 放一张模拟结论卡：
  > 质量状态：过程非受控 · 风险等级：中高 · 优先措施：**立即停机检查支撑系统**
- 立论文案：
  > 误判停机要担责，漏判不停机也要担责。一个质检工程师不会因为界面好看就按下这个按钮。
  > 工程师本来就有判断力。所以我的每一个设计决策，都在回答同一个问题：**怎么让他用得上自己的专业判断去核实这句结论，而不是被要求闭眼相信它。**
- 收尾一句直接交棒：**下面这 5 条，就是我在各层给出的答案。**

### 4. 签名决策 — 深挖 7 条最锋利的（提供深度）

**统一版式：每条四段** —— 场景（在哪、用户干嘛，一行）→ 决策（上层，人话）→ 证据（下层，术语翻译过）→ **取舍（我牺牲了什么来换）**。
按 4 个环节归组（质量 Agent / 沙盘 / 本体配置 / AI 管道生成器），读者顺一条线走，而不是被扔进孤立的点。

> 注：以下每条的「取舍」为草稿，请你核对是否与当时真实的权衡一致（尤其②的"太难看"、⑤的"显得不专业"是否真的是当时的反对意见）。

#### 环节一 · 质量 Agent（AI 给出会花钱的结论）

**① 可解释性外包给国家标准**
- **场景**：质量 Agent 判断"这批轴承的加工过程稳不稳"，要给出一个异常结论。
- **决策**：我不让 AI 用自己的话解释"为什么异常"，只让它引用工程师本来就认的国家标准。用户的验证成本，从"判断这个 AI 可不可信"降到"看一眼数字对不对"。
- **证据**：AI 不说"我觉得这里异常"，只说——*"依据国家标准（GB/T 4091）准则 1、第 34 组数据、均值越过控制下限。"* 对不对，翻一眼原始数据就知道；向上汇报时工程师说的也是国标，不是"AI 说的"。
- **取舍**：代价是 AI 的措辞被"锁"在国标术语里，不如自然语言顺口、也不能灵活展开——但在这个场景，可核验 > 好读。

**② 刻意暴露失败的工具调用**
- **场景**：Agent 分析时要调用外部计算服务，其中一次调用**失败**了。
- **决策**：我坚持把这行失败保留在界面上，没有藏起来。
- **证据**：对一个可能导致停机的系统，"永远顺畅"和"编的"在用户眼里没有区别。暴露 `call_r_service 失败` 这一行，等于给工程师一个可以怀疑的抓手。
- **取舍**：代价是界面不再"永远漂亮"，会被质疑难看——但当"漂亮"和"可信"冲突时，高风险场景里我选可信。**暴露失败是信任的成本，不是信任的损失。**

#### 环节二 · 沙盘推演（人要批量改写规则）

**③ 同一天，一个拒绝自然语言，一个接受**
- **场景**：在沙盘推演里，用户既要"覆盖某个属性值"，也要"配置一条会批量执行的自动化步骤"。
- **决策**：我在"属性覆盖"上**拒绝**了自然语言输入，在"自动化步骤"上**接受**了——两个相反的决定同一天做，因为它们的出错代价不一样。
- **证据**（小对照表）：

  | | 属性覆盖 | 自动化步骤 |
  |---|---|---|
  | 候选集 | 有限（来自本体 schema） | 条件组合近乎无限 |
  | 出错代价 | 高且**看不见**（编错字段名，用户发现不了） | 高但**有闸门**（提议卡可审阅） |
  | 结论 | **结构化表单** | **自然语言起草 + 结构化回显 + 采纳闸门** |

- **取舍**：属性覆盖那边用户要多点几下、不能打字，牺牲了输入速度——换来的是他不可能编造出一个界面里不存在的字段名。**自然语言用来加速，不用来替代。**

#### 环节三 · 本体配置（定义对象与关系）

**④ 让"配错"没有入口**
- **场景**：用户在配置两个对象之间的"关系"（如设备与轴承是一对多还是一对一）。
- **决策**：与其在用户配错后再报错拦下，我直接让错误的配置**在界面上没有入口**。
- **证据**：选了"一对多"，界面上根本不存在"外键放哪"这个选择器——用户配不出违反基数约束的映射。
- **取舍**：代价是不能用一个表单通吃所有情况，要为每种基数做不同布局，开发成本更高——但换来用户根本配不出错。**"错误不可能发生"永远优于"错误会被捕获"。**

**⑤ 把机器的"唯一编号"给人看**
- **场景**：用户在实体库里查看某个具体的零件实例。
- **决策**：系统给每个实体一个机器用的唯一编号，普通产品会把它当技术细节藏起来；我坚持让人也能看到。
- **证据**：这个编号（如 `ri.ontology...bearing.000143`）正是 Agent 引用某个实体时用的那个 token。人看不到它，就没法把 Agent 的输出和车间里那个实物对上，**审计链会在人机交界处断掉**。
- **取舍**：代价是界面上多了一串"技术味"的字符，可能显得不够干净——但它是人机核验的唯一物理入口，值。

> 收口：⑤ 与 §3 立论呼应——Agent 说"某轴承疑似异常"，工程师能不能自己走到实物前核一遍，靠的就是这个编号。

#### 环节四 · AI 管道生成器（让不写 SQL 的工艺工程师，自己搭出能上线的数据管道）

> 选点说明：本模块与沙盘（③）共享"生成与执行之间要有人类决策点"，为**避免重复**，此处**只讲 Vetex 没有的两把刀**——输入端防幻觉、画布即事实来源；共享的"确认闸门"原则留到 §6 收束点一次。

**⑥ 把幻觉挡在"说出口之前"（schema 前置防幻觉）**
- **场景**：工艺工程师用大白话让 AI 生成数据处理，最典型的翻车是 AI 编出一个**不存在的字段名**，还编得很像真的，等半夜管道跑挂了才发现。
- **决策**：我把当前能用的字段（列名 + 类型）常驻摆在输入框**正上方**，让用户"看着真实字段名说话"。
- **证据**：对着 `vibration_level`、`wear_level` 这些真实列名提需求，自然写不出不存在的列；万一写了"去除 nonexistent 列"，系统当场精确报错"该列不在可用列中"，而不是生成一段看着合理、跑起来才崩的 SQL。**幻觉的最佳治理点在输入端，不在输出端。**
- **取舍**：面板占了输入框上方的空间，字段几百个时要折叠/搜索——但换来错误在说出口前就消失了。

**⑦ AI 往画布"提案"，而不是接管画布（画布即唯一事实来源）**
- **场景**：最直觉的做法是纯对话——用户描述、AI 吐出一整条管道。但三个月后要改一个 JOIN 条件，只能重新对话，而对话不保证复现。
- **决策**：画布是唯一事实来源，AI 只当"节点生成器"。它生成的节点和手工拖出来的**完全同构**——一样能拖、能连、能删、能改名。
- **证据**：AI 明说"已生成 2 个操作节点"并逐条列出、提示可双击改名。**AI 加速的是搭建过程，不是替代了产物的可维护性。**
- **取舍**：放弃了"一句话生成整条管道"的演示惊艳感——但换来这条管道半夜跑挂时，有人能接手、能改。

### 5. AI 图标库 — 收尾彩蛋
- 保留现有三级链路视觉（图库检索 → AI 生成 → 上传沉淀）。
- 文案收敛成两句金句：
  > **AI 是兜底，不是入口。** 当确定性方案（图库检索）存在时，生成式能力应该被放在它失败的地方，而不是它前面。
  > 判断标准很简单：这个功能用得越多，AI 调用应该越少还是越多？越多，说明只是把 AI 接进来了，没让它沉淀。

### 6. 收束 — 6 条可迁移原则
以列表呈现，标题点明"换个行业也成立"：
1. 人定作用域，AI 在作用域内生成。
2. 生成与执行之间，必须有一个不可跳过的人类决策点。
3. 高风险的有限枚举决策用结构化表单；自然语言用来加速，不替代。
4. 可解释性外包给标准，比让模型解释自己更可信。
5. 暴露失败是信任的成本，不是信任的损失。
6. 机器侧的契约（编号、字段类型、接口名）必须对人可见，否则人无法验证模型。

结尾句：
> 这些原则成立于任何"AI 结论触发高成本动作"的场景——医疗辅助诊断、金融风控、运维告警。轴承只是它们第一次被验证的地方。
