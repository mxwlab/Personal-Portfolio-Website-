# Ask Mo：基于 Codex Harness 的个人 AI 工作台

> 状态：产品概念稿，待确认后进入 MVP 设计与实现  
> 项目：莫秀文个人作品集 / 个人品牌网站  
> 日期：2026-08-27

## 1. 想法概述

在个人作品集网站中加入一个面向招聘方与面试官的 AI 工作台。访问者可以通过对话了解莫秀文的职业经历、项目、真实贡献、产品判断和能力边界，并从回答直接进入相关案例与证据页面。

它不应是普通客服机器人，也不应冒充莫秀文本人。更准确的定位是：

> 一个可追问、可核验、知道自己边界的候选人 AI 工作台。

建议产品名：**Ask Mo**。

建议入口文案：

> 和我的 AI 工作台聊聊，了解我的经历、项目和产品判断。

建议身份说明：

> 这是基于莫秀文确认过的作品集、项目记录和职业经历构建的 AI 助手。它会引用证据；遇到未确认的信息，会直接告诉你。

## 2. 为什么值得做

这个功能不仅帮助面试官阅读作品集，也能成为新的作品集证据，同时证明：

- 能设计 AI 交互，而不只是描述 AI。
- 理解上下文、记忆、检索、引用和幻觉控制。
- 能把个人资料组织成真正可运行的产品。
- 重视个人贡献、团队贡献和事实边界。
- 能把 Agent 架构、可信体验与界面设计组合成完整产品。

现有项目已经形成较完整的证据基础：

- 工业智能语义基座：复杂 B 端 AI 交互与可信设计。
- D4S：复杂业务理解与企业级交付。
- 企业级智能体平台：真实上线的企业 Agent 平台设计经历。
- AI Continuity：Agent 上下文、隔离与交接。
- MeetingNotes：AI 评估、回退机制与本地优先。
- Wechat-CC：Agent 的入口、状态、记忆和长期关系。
- 口袋鱼塘：创造力、硬件交互和 AI 辅助原型。

Ask Mo 的作用，是把这些静态证据转化成可以按面试官兴趣动态探索的能力网络。

## 3. 产品原则

### 3.1 不是“AI 分身”

- 不冒充莫秀文本人。
- 不模拟私人情绪、人格或未经确认的观点。
- 不替本人做薪资、入职、承诺等决定。
- 明确说明回答来自已确认的公开资料。

### 3.2 证据优先

每个重要回答应尽量包含：

1. 简短结论；
2. 相关经历或项目证据；
3. 可打开的案例页面；
4. 必要时说明能力边界或待本人确认事项。

回答示例：

> 莫秀文的核心优势不是单纯完成界面，而是把复杂 AI 能力落成用户能理解、核验和操作的流程。
>
> 相关证据：工业智能语义基座、D4S、AI Continuity。

### 3.3 短回答、可继续追问

- 默认回答控制在约 150 字以内。
- 先给结论，再展开证据。
- 每次提供 2–3 个自然的后续问题。
- 长材料通过项目页面承载，不在对话里堆砌。

### 3.4 诚实归属

- 明确区分个人主导、个人交互落地、团队共创和产品定方向。
- 不把团队成果包装成个人主导。
- 不把项目目标写成已经达成的成果。
- 对尚未核实的贡献，使用中性表述或停止回答。

### 3.5 知道什么时候说“不知道”

建议缺少资料时使用：

> 现有公开资料不足以确认这个问题。我可以告诉你相关项目中已经确认的事实，或者你可以直接向莫秀文本人追问。

## 4. 核心用户与使用场景

### 招聘方快速筛选

目标：在 30–60 秒内了解候选人的定位、核心能力和代表项目。

### 面试官会前准备

目标：根据岗位要求生成值得深入追问的项目和问题。

### 专业面试深挖

目标：核验具体贡献、设计判断、团队边界、上线状态与能力短板。

### 同行或潜在合作方探索

目标：了解产品观点、独立项目与可能的合作方向。

## 5. 第一屏体验

不要只展示一个空白输入框。第一屏应主动提供高价值探索入口：

- 30 秒认识我
- 为什么我适合 B 端 AI 产品设计
- 看一个最能代表我的项目
- 追问我的真实贡献与能力边界

推荐问题：

- 你在工业智能语义基座里真正负责了什么？
- 哪些产品决策是你做的，哪些是团队共同完成的？
- 你如何处理 AI 结论的可信度？
- 你会写代码吗？独立完成过什么？
- 你的优势和目前的能力短板是什么？
- 如果加入我们的团队，你能解决什么问题？

## 6. 三种工作模式

### 模式一：快速认识

输出：

- 职业定位；
- 三项核心能力；
- 三个最相关项目；
- 当前求职方向。

### 模式二：深入追问

重点回答：

- 项目中的真实职责；
- 个人与团队贡献边界；
- 产品判断及其证据；
- 上线状态和未验证部分；
- 能力优势与短板。

### 模式三：岗位匹配

面试官可以粘贴 JD，系统输出：

- 明确匹配；
- 部分证据；
- 需要面试确认；
- 对应案例和建议追问。

不建议输出虚假的百分比匹配度。使用“明确匹配 / 部分证据 / 需要确认”更可信。

## 7. 为什么使用 Codex Harness

如果只是固定问答，普通 RAG 聊天机器人已经足够。Codex harness 的价值在于提供完整的代理执行循环，让工作台能够理解意图、检索多份证据、调用受限工具、维护会话上下文，并返回结构化结果。

建议把 harness 放在服务端，作为受限的代理运行层：

```text
面试官浏览器
    ↓
Ask Mo 网站界面
    ↓
网站服务端 API
    ↓
Codex SDK / App Server
    ↓
Ask Mo 专属 Agent
    ├── 公开事实库
    ├── 项目证据检索
    ├── 职业经历
    ├── 贡献归属与保密规则
    └── 页面导航等只读工具
```

Codex harness 在此负责：

- 维护单次面试会话上下文；
- 判断用户问题对应的能力与项目；
- 调用作品集检索工具；
- 组合多份已确认的证据；
- 返回回答、来源与下一步追问；
- 资料不足时停止推断；
- 对工具调用和结果进行结构化管理。

## 8. 建议提供的只读工具

第一版只开放小而明确的工具集合：

```text
search_profile(query)
get_project(project_id)
get_confirmed_contributions(project_id)
get_career_experience(experience_id)
compare_with_role(job_description)
open_evidence_page(page_id)
build_interview_brief(focus)
```

示例场景：

> 我们在招企业 AI 产品设计师，请结合这个岗位说明他为什么适合。

Agent 可以：

1. 分析岗位要求；
2. 检索对应经历；
3. 区分强匹配、部分匹配和暂无证据；
4. 生成候选人摘要；
5. 给出每项判断对应的项目页面；
6. 推荐面试中值得继续核验的问题。

## 9. 公开事实库设计

公开事实库必须与私人长期记忆分离。建议将每条事实结构化：

```json
{
  "id": "industrial-role-001",
  "claim": "莫秀文是工业智能语义基座项目的唯一交互设计师",
  "source": "industrial-semantic-base",
  "status": "confirmed",
  "ownership": "individual-role",
  "visibility": "public",
  "evidence_url": "/project-industrial-semantic-base.html"
}
```

建议字段：

- `claim`：可公开陈述的事实；
- `source`：事实来源；
- `status`：confirmed / needs-confirmation / private；
- `ownership`：individual / team / product-direction / unknown；
- `visibility`：public / private；
- `evidence_url`：对应作品集页面；
- `updated_at`：最后核验时间。

Agent 只能读取 `visibility=public` 且符合回答规则的内容。

## 10. Ask Mo 专属 Skill 草案

```md
# 身份

你是莫秀文个人作品集的证据型 AI 助手，不冒充莫秀文本人。

# 回答原则

- 只使用公开、已确认资料。
- 每个重要结论必须附来源。
- 明确区分个人贡献、团队贡献和产品方向。
- 不推断薪资、性格、离职原因等未确认信息。
- 不透露内部域名、客户信息和未公开项目资料。
- 资料不足时明确说不知道。
- 默认回答控制在 150 字以内，可继续追问。

# 输出结构

1. 直接回答
2. 相关证据
3. 能力边界
4. 推荐追问
```

## 11. 界面方向

界面应像“候选人能力检索台”，而不是网站右下角客服。

桌面端建议：

```text
┌──────────────────────────────────────────┐
│ ASK MO                         在线 · 有限知识库 │
├───────────────┬──────────────────────────┤
│ 探索路径       │ 对话与回答                 │
│               │                            │
│ 30 秒认识我    │ 简短回答                    │
│ 项目与能力     │                            │
│ 产品判断       │ 证据 01 · 工业语义基座      │
│ 真实贡献       │ 证据 02 · AI Continuity     │
│               │                            │
│ 已核验资料 8 份│ [继续追问] [打开案例]        │
└───────────────┴──────────────────────────┘
```

移动端建议：

- 顶部身份与有限知识库说明；
- 推荐问题横向滚动；
- 对话正文；
- 回答后的证据卡片；
- 底部输入框与隐私提示。

视觉语言延续当前网站：

- 暗青主背景；
- 薄荷绿作为主要强调色；
- “证据收据”式来源标签；
- 等宽字体展示机器状态和来源编号；
- 保持克制、专业和较强的信息层级；
- 不使用通用紫色 AI 渐变和悬浮客服气泡。

## 12. 公网安全边界

公开网站中的 Agent 必须与本机 Codex 和私人资料完全隔离：

- 不连接本地文件系统；
- 不暴露 ChatGPT 登录状态、Token 或 API Key；
- API Key 只存在服务端；
- 不提供 Shell、Git、文件写入或任意网络访问；
- 只允许调用白名单中的只读工具；
- 每位访客使用独立的临时会话；
- 设置频率、成本、上下文长度和执行时间限制；
- 对提示注入和越权检索做防护；
- 公开事实库与私人长期记忆严格分开；
- 默认不长期保存面试官对话；如需分析，必须匿名化并明确告知。

尤其不能让公网访客直接连接当前的 `ai-continuity`、共享记忆目录或本机 Codex App Server。

## 13. 第一版 MVP

第一版建议保持小而完整：

- 一个独立 Ask Mo 页面或首页明确入口；
- 一个 Ask Mo Agent / Skill；
- 一份人工核验的公开事实库；
- 4–6 个只读工具；
- 20–30 个高价值面试问题测试集；
- 三种探索模式；
- 每个重要回答附来源；
- 未命中事实时拒绝推断；
- 联系本人入口；
- 不开放 Shell、浏览器、写操作和私人记忆。

### MVP 验收标准

- 面试官在 30 秒内理解这个工作台能做什么。
- 关键问题的回答能定位到正确项目。
- 个人贡献与团队贡献没有混淆。
- 所有证据链接有效。
- 保密问题不会返回内部信息。
- 未确认问题不会被模型补全。
- 桌面端和移动端均可顺畅使用。
- 加载、回答中、无结果、拒绝、错误和限流状态完整。

## 14. 不做什么

第一版不做：

- 无限开放的数字分身；
- 与本机 Codex 的公网直连；
- 自动修改作品集内容；
- 长期保存访客完整对话；
- 多 Agent 炫技；
- 没有来源的自由回答；
- 虚构匹配度、项目指标或性格判断；
- 语音、Avatar、3D 人物等非核心装饰。

## 15. 推荐实施顺序

1. 确认 Ask Mo 的定位、公开边界和三种模式。
2. 从现有项目资料提取第一版公开事实库。
3. 建立 20–30 个问题与期望回答的评估集。
4. 定义 Ask Mo Skill 与只读工具协议。
5. 先做无模型的界面原型，验证信息架构。
6. 接入 Codex SDK 或 App Server 的服务端代理层。
7. 加入引用、拒答、限流和隐私机制。
8. 使用评估集测试贡献归属、事实准确性和保密边界。
9. 完成移动端、错误态与上线前安全审查。

## 16. 对外项目表述

建议最终在作品集中这样描述：

> 我基于 Codex 开放 agent harness 构建了一个证据型候选人 AI 工作台。它不是自由扮演我的数字分身，而是通过受限工具检索已确认事实，区分个人与团队贡献，并让每个重要判断都可追溯。

它应成为作品集的一部分，同时也是一个新的独立 AI 产品案例。
