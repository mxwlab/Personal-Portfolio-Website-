工业智能语义基座

质量 Agent 已上线 · 平台持续建设

Web · 两年项目

让算法给出结论时， 工程师仍看得见证据、留得住判断。

从轴承质量分析场景出发，连接工业数据、业务知识与 AI 应用，支撑质量分析、假设推演和数据处理。

一 平台背景

让分散的工业数据与知识，成为 AI 能理解的业务上下文。

工业数据分散在不同系统中，同一个对象可能有不同名称与口径，业务知识也难以直接用于计算和分析。AI 要理解这些数据，需要先明确它们代表什么，以及彼此有什么关系。

工业智能语义基座通过数据接入与处理、本体建模和智能应用，将数据、对象与业务关系组织起来，为不同工业场景提供共同基础。轴承质量分析是首个落地场景。

三 AI 管道

把处理需求转成可检查的流程，再交给系统执行。

具体问题

一次数据处理需求，最终要落实成数据之间的关联、筛选条件和转换步骤。依靠人工配置，操作者必须同时理解业务要求和数据结构，才能把业务表达变成可运行的流程。

为什么引入 AI

传统工具已经能执行数据处理，但业务人员仍要把需求拆成配置，或交给技术人员转换。继续增加配置项，仍把从业务表达转成数据处理规则的工作留给人。

我的判断

我的判断是，将这一过程设计为 AI 辅助数据处理工作流：由 AI 结合数据结构理解业务表达并起草方案，把人的工作从逐项配置转为审阅和修正。AI 在这里处理的是业务语言与处理规则之间的对应，预期减少需求到可执行方案之间的人工转换；字段、条件和关联仍由人核对，方案采用和执行仍由人确认，SQL 明确最终执行逻辑。

设计目标

01

减少业务要求变成处理规则时的人工拆解与转述

为了让 AI 起草真正减少逐项配置的工作，用户必须能基于具体方案检查和纠正理解偏差。方案因此把理解需求、修改配置和执行处理分开，避免起草结果未经核对就直接进入执行。

02

支持用户在同一方案上精确修改，并核对最终执行是否符合要求

流程采用“对话→意图确认→画布变更”：结合本次选定的数据集，回显计划操作和 SQL 逻辑，确认后再更新节点。实际运行前另做校验与确认，运行后通过日志和输出预览检查结果。用户确认的是具体处理要求，而不是对一句“是否继续”作出笼统授权。

三 AI 管道 / 关键决策二

让 SQL 可核对，保留精确修正入口

审阅方案后，用户可能已经知道哪一个字段、条件或关联需要调整。自然语言适合表达需求，SQL 能明确这些处理细节；对能够阅读 SQL 的用户，方案保留直接修改的入口，避免为了精确纠错反复改写问题。

四 质量 Agent

核对分析依据，继续追问和排查

具体问题

轴承出现质量异常后，相关的生产记录和质检结果分散在不同系统。异常发生在哪些对象上、对应哪些生产与检测记录，缺少集中、连贯的排查依据。

设计目标

01 将分散记录和指标组织到同一排查问题中， 减少跨来源的人工串联 02 保持追问所需的上下文，让工程师能从 已有分析继续核对和排查

为什么引入 AI

传统查询和报表已经能呈现记录与指标，但工程师仍要把不同来源的线索串起来，解释它们与当前异常的关系，并为下一轮排查组织问题。增加查询页或筛选项，仍把语义理解和上下文组织留给人。

我的判断

我的判断是，AI Agent 的语言理解与上下文组织能力适合承接这部分工作：围绕当前问题解释已有事实，连续回应追问，预期减少人工拼接信息和反复补充背景的工作。统计数值仍由程序计算；解释必须有可核对的来源，原因假设仍由工程师核实。

四 质量 Agent / 关键决策一

结构化内容契约组织可核对的报告

若解释仍是一整段文字，工程师还要自行拆出指标、告警、来源和原因假设。方案因此用内容契约组织这些信息，使审阅可以逐项展开，不把结构是否正确完全交给模型每次生成的文字。

报告中的目录、章节、指标、告警、表格、状态与说明分别承载业务信息，并具有明确的字段和引用关系，前端可以按约定处理。下面的实例展示章节与键值指标如何组织，而不只是给一段文本加样式。

四 质量 Agent / 关键决策二

计算、报告生成与模型解释分开

在排查过程中，工程师需要一组可以反复核对的指标作为依据。方案因此让程序按明确口径计算数值，模型围绕这些结果和可核对的来源解释，原因假设仍需进一步核实。

指标由程序计算，分析面板与报告使用同一份结果，保持数值一致。工程师可以沿来源记录和业务图谱，核对数据依据。

五 沙盘推演

业务假设成为可审阅的规则

具体问题

以当前轴承质量场景为例，发现异常后，业务还要决定哪些轴承需要复检。调整判定规则会影响复检范围，但新增哪些对象、哪些复检标记或质量状态会改变，缺少直观的判断依据。

沙盘首先要提供实施前的比较依据：固定同一批次全部轴承的分析快照，查看规则调整对复检范围和逐件状态的影响。工程师可以先核对新增或移出的轴承及其标记变化，再决定是否采用方案。

为什么引入 AI

在规则表达上，传统配置已经能明确条件和动作，再由程序执行推演；但业务人员仍要把设想拆成对象、条件、动作和执行顺序。继续增加配置控件，并不能省去从业务设想到规则表达的人工转换。

我的判断

我的判断是，将沙盘设计为 AI 辅助规则起草与编排推演工作流：用 AI 对自然语言的理解形成规则草案，把人的工作转向审阅条件、修正动作和比较方案，预期减少逐项翻译复杂设想的工作。手动入口继续保留，人决定规则是否采纳及如何调整，程序负责按确认后的规则计算结果；模型生成的解释不能代替仿真结果或因果判断。

五 沙盘推演 / 设计目标

在实际处置前，比较规则下的影响

01

比较复检范围与状态变化

在实际处置前比较基线与方案的复检范围和状态变化，为复检对象的选择提供依据。

02

形成可检查的规则草案

先把业务设想形成可检查的规则草案，减少逐项手动配置的工作。

03

让两种入口进入共同计划

便于调整步骤，并结合基线、修改条件和规则比较方案。

五 沙盘推演 / 关键决策一

双入口表达，共用结构化计划

要比较复检范围，方案中的条件和动作必须能够被明确执行。AI 起草若仍留在自然语言里，用户还得把建议重新翻成配置。两种入口因此统一为 WHEN·ALL 条件与 FUNCTION 动作，供用户检查“在什么情况下，对什么对象，做什么修改”。

自然语言建议经过采纳才进入步骤计划，之后仍可编辑、调整顺序，再发起推演。采纳与运行分开，让“正在考虑的建议”和“准备执行的规则”保持明确区别。若只是直接修改某个具体值，则由属性覆盖承担，保留对象、属性、原值与覆盖值的对照。

共同计划

五 沙盘推演 / 双入口

条件与动作分别审阅

“当质量状态为 FAIL 时，将需要复核设为 true”

两种入口都需要明确条件和动作，自然语言起草将它们分别回显，手动配置则逐项填写。

自然语言起草

待审阅建议、条件与动作，采纳或放弃。

手动配置

逐项明确条件、对象和写入值。

五 沙盘推演 / 关键决策二

结果受假设与规则约束

复检方案的差异必须能回到具体规则与对象上核对。结果因此同时呈现基线与方案的复检数量、新增及移出的对象、逐件状态、原值与覆盖值，以及命中步骤和 MES／QMS 来源。

沙盘回答的是“按这组规则，哪些轴承会被标为需复检、哪些质量状态会改变”，不能由模型凭语言生成一份看似合理的推演结果。

六 结果与反思

交付：让设计判断有可核对的依据

我与产品、算法和研发协作，将数据处理、质量分析和假设推演推进为产品方案。管道以本地合成数据验证 SQL 审阅、保存与执行，修改条件后输出由80条变为2条；质量分析通过报告和视频呈现来源核对与连续追问；沙盘明确规则起草、编辑和运行的衔接。

成长：先判断 AI 要承担哪部分工作

我的关注点从操作是否顺畅，延伸到业务问题是否需要 AI：现有工具已能完成什么，人工还承担哪些转换与组织工作。质量分析需要在限定范围内选择工具、组织上下文并解释结果；管道和沙盘则更适合用 AI 辅助起草方案。不同场景采用不同形态，人负责审阅与判断，程序负责计算和执行。

反思：流程跑通后，还要验证业务价值

本页展示了流程衔接，并验证了部分实现，业务价值仍需真实任务检验。后续需要观察人工配置、信息拼接和规则转译的负担是否减少，并结合修正次数、完成时间与结果正确性，判断 AI 带来的便利是否足以覆盖核对成本。
