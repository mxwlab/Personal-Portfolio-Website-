项目介绍

切换工具时，项目背景也需要一起交接。

AI Continuity 面向在 Claude Code 与 Codex 之间切换、持续推进同一项目的使用者。它在本机为接入的项目保存交接状态与近期对话，并在支持的命令行启动路径中，将这些内容交给下一次工作。

做这个产品的起点，来自我自己的跨工具协作：目标和取舍散落在不同对话中，切换之后需要重新说明背景，已经确定的事情也可能被再次讨论。我希望下一位 AI 能知道当前走到哪里，让人继续推进任务。

用户安装工具后，选择需要接入的项目，日常仍使用熟悉的 Claude Code 或 Codex 命令。当前自动接续路径面向 macOS 与 zsh 命令行；桌面端通过项目中的上下文文件辅助读取。

我和 AI 的分工

把重复解释的负担，拆成可以实现的产品机制。

我负责定义问题、划定边界和做取舍；代码由 AI 子代理按我拆好的任务逐个实现。整个产品按 7 个任务推进，每一步先写测试，再实现和复查。

我负责

  • 定义问题：换一个 AI 就要重讲背景，多个项目之间还会串线。
  • 划边界：本地优先，原始事件 30 天后脱敏；第一阶段只接 Claude Code 与 Codex。
  • 设计交接内容、接入流程和退出方式。
  • 做取舍：下面四个判断，每一个都要为代价负责。
  • 验收：用自己的真实项目，跑 Claude Code 与 Codex 的双向交接。

AI 负责

  • 按任务逐个编写代码和自动化测试。
  • 编写一行安装器、中文使用说明和 Welcome 引导页。
  • 复查实现，修复发现的缺陷。
  • 整理公开发布版本，去掉内部文档和真实路径。

01

交接内容

让下一次工作有明确起点。

历史越来越长，当前状态仍需要清楚。

项目讨论会包含已经放弃的想法、修改过的要求和仍未解决的问题。如果把这些内容一起当作当前依据，下一位 AI 仍然需要判断哪些决定有效、下一步该做什么。

我将交接内容组织为一份可更新的当前状态：目标、用户意图、约束、已确认决定、开放问题和下一步。近期对话补充必要语境，帮助理解当前状态形成的上下文。

两类内容，承担不同的交接任务。

当前交接状态

目标、用户意图、约束、已确认决定、开放问题和下一步。随当前任务变化而更新。

近期对话

补充相关表达与现场信息，帮助下一位理解当前状态的上下文。

当前状态与近期对话，承担不同作用。

交接状态明确当前要继续的工作，近期对话保留相关表达与现场信息。状态发生变化时更新交接，普通对话则进入事件记录。

这一处理控制了每次交接需要携带的内容，也意味着它依赖及时维护：如果新决定没有被记录，保存下来的状态就可能滞后。因此，项目接入同时加入记录与更新规则，要求兼容的 Agent 在工作过程中维护交接。

从绑定一个项目，变成按项目接入。

早期接入路径绑定单个项目。扩展到多个项目后，每个项目都需要自己的目标与上下文，接入过程也需要能够重复执行。

我将使用路径整理为“安装一次，按项目开启”。项目通过本地标记关联自己的交接记录，在项目目录及其子目录启动时，读取对应上下文；未接入的目录继续按原有方式启动。

这一选择将是否启用连续协作交给使用者，也增加了一次明确的项目接入操作。同名项目需要指定不同标识，确保各自的记录能够被正确区分。

02

日常接续

延续熟悉的工作入口。

在开始工作时，就交付需要的上下文。

如果每次切换后都要提醒 AI 先读取背景，交接仍然需要人持续照看。我将上下文载入放在支持的命令行启动路径中：先根据当前项目整理交接与近期对话，再交给启动的工作端。

日常操作因此延续原有习惯。使用者进入已接入的项目，启动 Claude Code 或 Codex，就能将已记录的项目状态带入这次工作。

使用流程示意

安装一次，按项目开启。

选择项目

照常启动

在项目内启动 CLI，载入交接状态与近期对话。

03

维护与接续

Agent 依照规则记录变化，为下一次工作保留状态。

自动载入与记录维护，各自有明确位置。

启动流程负责把已有上下文送到工作端，MCP 工具提供读取、追加事件和更新交接的能力，项目规则则引导 Agent 在工作过程中维护记录。

这些环节共同支持下一次接续：开始时读到状态，工作中记录变化，结束或切换后有内容可以继续。桌面端采用辅助读取文件的方式，具体接续仍依赖工作端读取项目规则与上下文。

不同入口，有不同的接续方式。

命令行 · 自动载入

支持的 macOS / zsh 启动路径在工作端启动前准备上下文。

桌面端 · 辅助读取

通过项目规则和上下文文件辅助接续，依赖工作端实际读取。

验证与调整 · 让交接发生在开始工作前

早期方案依靠工作端主动读取交接信息。历史验证记录指出，只提供 MCP 工具并不能保证工作端会调用它，因此把命令行接续调整为启动前注入上下文；桌面端则保留项目文件辅助读取，不承诺相同的自动接续方式。

双向交接的历史记录记载：Codex 写入版本 1，Claude 读取后写入版本 2，Codex 再读取并写入版本 3。这是两端读写同一交接状态的验证记录。

读取失败时，先停下来处理。

在已接入项目中，如果无法生成上下文，启动流程会停止并返回错误。使用者需要先处理接续问题，再启动工作端。

这会打断一次启动，但能让故障在开始工作前暴露出来，避免使用者以为背景已经载入，而 AI 实际上缺少当前目标和决定。

03

更新与退出

让状态更新与接入管理有明确边界。

更新交接之前，先确认依据是否仍然有效。

多个工作端可能先后修改同一项目的状态。如果一个工作端仍依据旧版本提交更新，就可能覆盖另一个工作端刚保存的决定。

交接更新因此带有版本检查。提交时的版本与当前版本不一致，就明确返回冲突，要求读取最新状态后再处理。

这一机制增加了冲突处理步骤，换来的是过期更新不会直接覆盖新的交接。它解决版本一致性问题，内容本身如何取舍，仍需要结合最新记录判断。

项目可以退出，已有记录如何处理也要明确。

接入会增加项目标记、规则和本机配置。我将退出与卸载纳入使用流程：可以移除单个项目的接入，也可以卸载全局集成；默认保留本地数据，清除数据通过显式选项执行。

日常保留策略则定期清理超过 30 天的原始事件正文，保留必要元数据。交接状态用于延续当前任务，原始对话有自己的保存期限。

上下文由本机实例管理；被工作端读取后，会进入用户所用 Agent 的工作上下文。产品范围聚焦同一台电脑上的项目接续。

证据

不只设计出来，也让它跑通、可以交给别人装。

  • 双向交接跑通Codex 写入版本 1，Claude Code 读取后写入版本 2，Codex 再读取并写入版本 3，两端读写同一份交接状态。
  • 复查发现 6 个缺陷例如：两个同名文件夹的项目会用到同一个会话和后台任务，正是要防的串线，改为“目录名 + 路径哈希”区分；不合法的项目名会在写入后才失败、留下半接入的状态，改为写入前先校验；项目标记文件改为只解析不执行，避免运行任意代码。
  • 120 项自动化测试覆盖双向交接、项目隔离、显式切换项目、纠错可追溯、并发写入不静默覆盖，以及安装、接入、退出、卸载和发布检查。
  • 可以交给别人装MIT 开源，一行命令安装；装好后自动打开四步 Welcome 引导页，配中文使用说明。

当前结果

从自己的协作习惯，推进到可以接入和退出的工具。

AI Continuity 已以 MIT 协议开源，提供安装、项目接入、验证、退出与卸载说明，并持续用于我自己的跨 Agent 工作。

我的工作从定义交接内容，延伸到项目边界、启动流程、版本冲突和数据保留，将“换工具后接着做”拆成可执行的规则与操作。

当前重点是支持的本机命令行接续与桌面辅助读取。后续评估仍需要关注实际切换时有没有遗漏新决定、接入是否容易理解，以及失败后能否顺利恢复工作。
